## Native implementation and build

`src/attachments/archive/ArchiveTransformer.{h,cpp}` consumes a captured `QByteArray`, existing `FileDescriptor` and `FileReadParams`, limits and optional cancellation flag. It returns the existing `FileTransformResult`. `FileTransformer::fromBytes` now dispatches ZIP/JAR/WAR, TAR and TGZ/TAR.GZ to it; public transformer signatures remain unchanged. This makes the existing attachment-preparation seam use archive listings, while root-owned formatted read/ls integration remains separately tested. The prior ordinary directory renderer retains its 200-entry limit; archive rendering uses 500.

The code opens no member path and returns no member contents. ZIP parsing reads central/local record metadata and encoded extents only, without decompressing individual members. TGZ uses a 32 KiB output buffer to feed a streaming TAR header/skip reader; member payload bytes are skipped and never persisted or interpreted. No mounting, subprocess, Node, shell helper, network or credential API exists in this module.

Build target requirements: add archive implementation/header to `ade_file_transformer`, require/link `Qt6::ZlibPrivate`, and register `tests/test_archive_transformer.cpp` linked with that target and QtTest. The static Qt SDK supplies prefixed zlib **1.3.2 (Qt)**. The isolated gzip-initialization/link probe succeeded. `objdump -p` showed only Windows system/UCRT imports, no zlib or compiler-runtime DLL. No new downloaded runtime or vendored decompressor is needed. Preserve the existing Qt source/distribution notices plus `src/attachments/archive/ZLIB-NOTICE.txt`, copied from the installed zlib header's complete notice. `audit/archive-transformer-provenance.json` records source/SDK archive hashes and references.

The listing/tree semantics are adapted from the pinned Stagewise source, retaining root AGPLv3 attribution. ZIP layout was checked against PKWARE APPNOTE 6.3.10 and filename/listing behavior against the pinned dependency's yauzl 3.3.0 source. Those documents are references; no JavaScript library implementation or PKWARE document is bundled. The CP437 table contains standard high-byte mappings generated from Windows .NET's code-page 437 decoder. The C++ parser is native code, not a translated dependency runtime.

## Source behavior and explicit boundaries

- ZIP central-directory scanning handles ordinary and ZIP64 end records, ZIP64 size/offset extras, CP437 and UTF-8 names, and CRC-qualified Info-ZIP Unicode-path extras. Backslashes normalize to slashes; absolute, drive-prefixed and `..` ZIP names are rejected as by the source dependency. Names and member data are never filesystem destinations.
- Compressed/encrypted ZIP file contents are not decoded. Central listings for methods other than stored/deflate remain available, with `unsupportedContentMethods` metadata. Traditional-encrypted entries are identified as `encryptedContent:listing-only`. Split archives, strong-encryption records and unknown container extensions return explicit unsupported outcomes. There is no password, extraction, arbitrary decompressor or unknown-format probing promise.
- TAR lists regular files, directories and symlinks from 512-byte headers and optional USTAR prefixes. GNU long-name/PAX records are skipped with their bodies; they are not interpreted. Stop at the first zero header, matching the source. Traversal-looking TAR names are displayed as inert tree segments rather than normalized into filesystem paths. Directory metadata counts only explicit archive directory entries. The last duplicate path wins its rendered node, while metadata counts all listed records, matching the source map construction.
- Listing stops at 2,000 entries and marks `2000+ entries`, including exactly 2,000, as in the source. Preview is depth zero; full default depth is four. Rendering sorts directories first with en-US Qt collation, uses per-level caps 20/10/5 and a separate 500 displayed-entry bound, with source-style file sizes and truncation notices. Effective preview parameters are `{preview:true, depth:0}`.
- Gzip CRC/trailer validation and concatenated members are supported within bounds. An entry-limit early stop adds `gzipIntegrity:not-verified-after-entry-limit`; it never asserts integrity of an unvisited trailer. Known decoder errors are rejected before accepting an entry-limit result. Complete decompression does not imply all TAR members were listed past the cap.

Default native bounds: 64 MiB input, 128 MiB inflated bytes, 2,000 listed entries, 20,000 TAR headers, 10,000 implied tree nodes, 32 path components/depth, 4,096 name bytes/characters, 65,536 inner text characters, 8,192 inflate calls and 16 concatenated gzip members. Limit values are checked. All offsets/extents and size totals use checked unsigned arithmetic. Header/name parsing and each inflate/render iteration check cancellation. The inner text cap also covers error display parts; `result.error` remains a separate bounded diagnostic. XML envelope overhead is governed by the existing FileTransformer contract. Hard cuts clear range/depth coverage and set `coverageKnown=false`.

Intentional native corrections/differences: reject invalid whole-name UTF-8, NUL names, bad TAR checksums, malformed octal fields, base-256 TAR sizes and incomplete TAR payloads. ZIP local-header/payload extents are verified, stricter than yauzl's central-only listing. A false EOCD signature inside an otherwise valid comment is skipped; yauzl 3.3.0 instead fails at that first candidate. Archive error diagnostics are explicit rather than the source's generic raw-read fallback. Gzip streaming bounds prevent the source's unbounded accumulation. Names containing newline/tab/backslash are escaped in display. Locale edge cases and JavaScript's rounding of enormous integers are not claimed identical.

No PDF/RAW/ISO/DMG or AST support was added. GNU/PAX name interpretation, arbitrary archive formats, member extraction, archive editing, per-member data integrity, encrypted-content decoding, universal corruption detection and fuzz-complete coverage are not implemented or claimed.
